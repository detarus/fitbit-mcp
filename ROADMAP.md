# fitbit-mcp — дорожная карта

Последнее обновление: 2026-10-17.
Стадия: alpha; первая CI-матрица прошла на трёх ОС. Реальные аккаунты и клиенты ещё не проверены. npm-пакет не опубликован.

## Цель и границы

Открытый MCP для Fitbit через Google Health API: чтение показателей, запись питания и воды, плагины и скиллы Codex и Claude Code, поддержка macOS, Windows и Linux.

Универсальная интеграция разных производителей будет отдельным проектом. В этом репозитории не строим SDK адаптеров других трекеров.

Первое реальное устройство для проверки — Fitbit Air. Первая локальная платформа — Mac. Версия устройства, сообщённая пользователем: 20001.253.2; версию macOS нужно уточнить при настройке. Персональные показатели и секреты в репозиторий не попадают.

## Статусы и порядок работы

- DONE — результат создан и проверен; указано подтверждение.
- DONE — запланировано, работа ещё не начата.
- DONE — задача выполняется.
- BLOCKED — работа остановлена конкретной зависимостью; причина и следующий шаг записаны.

Порядок определяется этапами и зависимостями, без неподтверждённых календарных обещаний. Этапы можно частично выполнять параллельно, если зависимости закрыты. Исполнитель разработки — сопровождающий проекта с ИИ; вход в аккаунт, настройка OAuth и проверка в приложении требуют участия владельца аккаунта.

## Текущий фокус

Текущий фокус: первая alpha готова к ручному тестированию на Mac; инструкция — [docs/TESTING.ru.md](docs/TESTING.ru.md).
Проверки на реальном аккаунте требуют входа владельца; до этого соответствующие задачи не отмечаются DONE.

Облачная среда недоступна. Код подготовлен через GitHub-коннектор. Сборка и синтетические тесты проверены GitHub Actions, lockfile сохранён. Подробности — [docs/VALIDATION.md](docs/VALIDATION.md).

## Как поддерживать этот план

1. Перед началом задачи прочитать актуальный ROADMAP.md и проверить фактическое состояние репозитория.
2. Для начатой работы поставить IN PROGRESS; для блокировки — BLOCKED с причиной, зависимостью и следующим действием.
3. В том же PR или наборе коммитов, который завершает работу, обновить статус, дату и подтверждение: код, PR, коммит или отчёт проверки.
4. Не ставить DONE по одному плану, наличию кода или успешному HTTP-ответу: должны выполняться критерии строки.
5. Разделять проверку на синтетических данных, CI и реальном аккаунте. В отчёты включать только обезличенные результаты.
6. После изменения приоритетов обновить «Текущий фокус». Новым задачам выдавать стабильные ID, существующие ID не переиспользовать.
7. Держать README кратким и ссылаться на этот файл, чтобы не вести два расходящихся списка задач.
8. Поддерживать план во время активной работы над проектом. Фоновый мониторинг и автоматическое обновление отдельно не настроены.
